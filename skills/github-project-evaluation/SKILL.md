# GitHub Project Evaluation (merged skill)

This Skill merges the former `discover-open-source-projects` (Stage A) and `design-project-tests` (Stage B) into one unit. Stage A finds and statically evaluates candidate repositories; Stage B turns a frozen first pass into test designs and, only under separate explicit authorization, executes bounded isolated tests. All original boundaries, gates and BLOCK rules carry over unchanged.


# Stage A - Discover and First-Pass Evaluation

Input: domain/task, desired roles (engine, library, UI, data, research), license/region/runtime constraints, accessible networks and review budget. Distinguish **DISCOVER** (public metadata, no clone) from **DEEP REVIEW** (frozen source checkout with separate scope). When the user gives a ranking URL, treat its current query/page as a starting hypothesis, **not** a complete candidate universe.

r4 adds a bounded exact Chinese intent lexicon, goal-role metadata triage, tracked Gradle/JVM inventory and sparse-first acquisition. Read [intent and acquisition contracts](references/intent-and-acquisition.md) for query provenance, limits and hard-quota BLOCK behavior before using them. Use a caller-owned private `0700` cache; unsafe existing permissions are rejected rather than silently changed. Signature verification uses a trusted OpenSSL with Ed25519 support selected by absolute `OPENSSL_BINARY` or PATH. Missing Linux isolation remains BLOCK. Bundle-level `tools/doctor.py` and `tools/handoff_check.py` are not installed as part of an individual Skill folder.

## Workflow

1. Read [source and cache boundaries](references/sources-and-cache.md) before network operations. Check `robots.txt`, site availability and GitHub rate limits; note HTTP 403 separately from a genuinely empty result. Never work around authorization, login, robots denial or CAPTCHA. Use HTTPS allowlisted routes; no arbitrary-URL crawling or token logging.
2. Expand the user's intent to synonyms and *counterexamples* (for 量化: financial trading/backtesting versus mere numerical quantification). Search Kaiyuanbang, RepoRank's English public search, GitStar's limited search catalog, and GitHub Search API with `--source multi`; combine by canonical `owner/repo`, never by title. RepoRank is a **same-operator mirror**, GitStar is an independent but **catalog-only** site with no validated full pagination; the latter always contributes leads marked PARTIAL rather than a false exhaustive search. Report provider coverage/failure separately. Do not equate site rank, stars, freshness or descriptions with functional fitness. Read [selection method](references/selection-and-deep-review.md).
3. Run `python3 scripts/discover.py '量化' --source multi --max-pages 25 --verify-top 8 --cache-dir <private-cache> --output-dir <new-run-dir>`. `multi` includes a limited GitStar catalog, so exit 2/PARTIAL is expected even when all requests succeed; evaluate per-source `coverage` instead. Exit 0 in exhaustive-source modes only means **requested bounded pages** were collected, not a full internet search or passing project review. For isolated fallback choose `--source site`, `--source reporank`, `--source gitstar` or `--source github`; document omitted providers. If upstream is unavailable use `--offline` with hash-checked per-source cache or query-matched Kaiyuanbang `--seed-dir` (`.query` and `page-N.html`; seed only applies to Kaiyuanbang). No cache/network means PARTIAL/empty, never fabricate names or force green. Other web search tools may supply manually attributed leads but are not CLI adapters; never bypass robots, 403 or rate limits.
   For a literal `owner/repo` query, if GitHub Search fails without rows, the CLI makes one bounded request to the allowlisted GitHub repository metadata endpoint. An exact match appears with source `github-direct` and scope `exact-only`, while Search and overall collection remain **PARTIAL**; metadata presence is not commit-SHA verification. A hit from a writable local cache remains `cache_trust=local-unverified` and must not be called fresh GitHub verification.
4. Review `candidates.json` and `SHORTLIST.md`. Produce a human-curated shortlist by role with links, strengths, evidence source/time, unverified fields, and why each was included/excluded; discovery score is a **preliminary search heuristic**, not project quality or investment advice. For a fixed C mathematical library requirement use `--require-language C --require-role library --concept-any mathematical --concept-any arithmetic`: metadata conflicts cannot auto-shortlist, unknowns stay unknown, matching low-score items appear only as `role_review_leads` for manual investigation. This is not source-code proof and may miss true libraries; rerun synonyms rather than stuffing the list. For directional conversions such as `text-to-video`, the ordered phrase reduces reverse-direction/word-bag noise, but a tutorial or unrelated suite may still qualify by mention alone: explicitly separate runnable generators, research, prompts, downloaders and tutorials before recommending anything. A research paper can have a lower score than a popular tutorial; freeze positive/negative labels and quantify errors on each query before claiming good search precision. If only a site snapshot is available, mark repo URL, license and activity **pending GitHub verification**. Read [output contract](references/discovery-output-contract.md).
5. Perform the [repository first pass](references/first-pass-evaluation.md) **inside this Skill** for each shortlisted candidate with an authorized frozen local checkout: run `python3 scripts/evaluate_first_pass.py <checkout> --expected-repo owner/repo --discovery-file <candidates.json> --output-dir <new-output-dir>` (omit discovery only when unavailable and label the gap). Read README/Start/Quickstart, architecture and manifest, source entrypoints, tests/CI, license and security docs; produce `FIRST-PASS.json`/`.md` **and** a reviewer-written `FIRST-PASS-ASSESSMENT.md` with cited code evidence and goal-specific rubric. If the user's goal is to learn better design rather than deploy a candidate, additionally follow [design learning](references/design-learning.md) to produce a manually evidenced `DESIGN-INSIGHT.md`; distinguish project mechanisms from reusable principles and recommend direct reuse/thin adaptation before new implementation. Before publishing any model review as a decision, run the [review claim audit](references/reviewer-claim-gate.md) against the raw model text, first-pass report and any independent execution record. It emits a separate `REVIEW-AUDIT.json` with `BLOCK` and nonzero exit for this stage; a model's “approved for deployment” contradicting that gate must be surfaced as an evaluation failure, not copied into a recommendation. Script score only measures static evidence coverage; until manual goal-fit review and upstream identity/permission checks, deployment test gate stays BLOCK. Missing checkout stays BLOCK instead of receiving fabricated scores. **Do not run repository scripts in this stage.**
6. If the first pass meets the handoff contract, design a **separate** authorized functional/deployment/pressure test with frozen commit, independent business oracles, resource limits and isolated execution; never execute the project merely because the first-pass score is high. For a Web/mobile UI candidate, hand off the optional TesterArmy/e2e execution route to Stage B of this Skill for a separately authorized UI test; it does not replace the domain oracle or pressure/safety tests. For finance specifically check lookahead, point-in-time data, slippage/fees, fake orders and risk stops without live trading; unrelated domains use their own oracle. When separately authorized execution already produced logs, [validate local execution evidence and optional reviewer signature](references/execution-evidence-v2.md) before handing off; crypto validity and integrity are not business approval. The downstream test-design stage, not this first pass, judges functional PASS/FAIL/BLOCK.
7. When explicitly asked to mount Loop-dev, use the [native Loop discovery adapter](references/loop-integration.md) for existing `online/snapshot/negative` runs; for a **bounded, offline** discovery → static first-pass workflow use the separate [native first-pass runner](references/loop-first-pass.md), with a preexisting authorized checkout under the task root. The offline runner is not the online multi-source workflow: to claim multi-source coverage the Skill still needs the `discover.py --source multi` result and per-provider gaps. Neither Loop runner can safely execute untrusted repo code or turn Verify into product acceptance. Challenge the Skill with [test plan](references/test-plan.md), preserve failures and rerun on a fresh workspace after changes.

When site and GitHub summaries disagree, ranking uses GitHub name/summary/language; `site_title`/`site_description` are only audit evidence. Cached GitHub metadata is still not fresh upstream verification; explicit GitHub zero Stars cannot be replaced by site Stars.

Before claiming upstream identity for a frozen checkout, add `--verify-upstream` to `evaluate_first_pass.py`: it requests the allowlisted GitHub commit endpoint without local cache and compares the returned SHA with local `HEAD`. Inspect `identity_gate` and `upstream_commit_verification`; no flag, origin mismatch, 403, timeout or SHA mismatch stays BLOCK. `triage=REVIEW_CANDIDATE` alone never clears this gate, and even `identity_gate=PASS` never approves execution or deployment. The offline Loop first-pass adapter does not perform this online step.

For separately authorized, explicitly predeclared, short local project probes, use the [bounded isolated-worker trial](references/isolated-worker.md) after the identity gate; missing Linux `bubblewrap`, failed namespace preflight, changed task spec or unavailable upstream identity must block. This trial is not an audited universal sandbox, a pressure-test engine, or permission to execute arbitrary unknown repositories.

For project-specific functional, recovery and pressure **design** after a first pass, hand off the frozen `candidates.json` and `FIRST-PASS.json` to Stage B of this Skill (read `references/discovery-handoff.md`). Design does not authorize execution; keep `PARTIAL`, `identity_gate=BLOCK` and all open risks visible in its `TEST-HANDOFF.md`.

For architecture decisions, additional ranking adapters, multi-query pagination and the staged rollout read [architecture and rollout](references/architecture-and-rollout.md).
For an end-to-end Loop-owned repository evaluation and testing workflow with domain-swappable acceptance gates, read [Loop project evaluation blueprint](references/loop-project-evaluation-blueprint.md); it explicitly distinguishes implemented discovery from planned deep review and pressure stages.
For the broader training/evolution loop and concrete video, defensive vulnerability research and quantitative price-volume **design examples**, read [Loop training architecture v2](references/loop-training-architecture-v2.md). These are planned acceptance routes, not implemented domain agents.

## Hand-off rules

- Preserve `query`, `source_mode`, `status`, `coverage`, `rows_seen`, `provenance` (source URL/observation time/SHA-256/cache-trust), `errors`, `candidates`, `shortlist` and `acceptance=NOT_REVIEWED`. If pagination count differs or one provider fails, status is PARTIAL even when the other provider succeeds. `COMPLETE` is only requested-source pagination completion, never verified repository existence or an entire GitHub universe.
- Keep full raw pages only in private, bounded TTL cache; output metadata only, no cookies, credentials or copied proprietary files. Prefer user-supplied offline snapshots when networks are unavailable, with exact query matching and explicit provenance.
- Never call a discovery report a comprehensive test of any repository. Cite the source/commit and independent evidence for second-pass verdicts.

# Stage B - Design and Authorized Execution of Project Tests

Produce **two project-specific design documents**, not a generic checklist: `FUNCTIONAL-TEST-DESIGN.md` and `PRESSURE-TEST-DESIGN.md`; include `TEST-HANDOFF.md` for evidence links, decisions and execution authority. Read [output contract](references/test-design-output-contract.md) before writing. Use [routing](references/project-routing.md), [functional method](references/functional-method.md), and [load method](references/pressure-method.md) as applicable. Read [source mapping](references/source-mapping.md) if incorporating the user's `legacy internal test-server assets` guides or earlier Loop evaluation.

Choose the mode explicitly: **DESIGN** needs only read access and produces the three documents; **EXECUTE** requires separate user permission and follows [execution method](references/execution-method.md), plus `TEST-EXECUTION.json` and `EXECUTION-RESULTS.md`. Do not silently convert a design request into load injection. Source-code repair is a separate approval/scope decision; improving this Skill does not make a failing project green.

When Loop-dev must **actually execute** a project's frozen native suite/gate, use [native Loop runner](references/native-loop-runner.md). The `agent_prompt` TaskRunner runs approved, shell-free commands with a cumulative budget and persists original outputs. It does **not** generate tests, fix the project, approve performance capacity, or turn Loop Verify into release acceptance.

For this r3 distribution, read [runtime and recovery changes](references/runtime-r3.md) before native execution or restoring a run: the adapter requires input-bound state v2 and explicitly distinguishes stage completion from full-plan completion. Never migrate an old successful journal by adding fields or copying its status.

When following a Stage A discovery/first-pass run, read the [discovery-to-test handoff](references/discovery-handoff.md) and preserve source/commit identity, discovery coverage gaps and original blocked gates. Use the [cross-project error-learning method](references/error-learning-loop.md) in `TEST-HANDOFF.md` so recorded failures become scoped, reviewed regression cases rather than unverifiable RAG conclusions. For unknown third-party code, the discovery stage's bounded isolated-worker trial ([isolated worker](references/isolated-worker.md)) is an optional short-probe route, not authorization for native Loop commands or pressure testing.

## Procedure

1. **Scope and inspect.** Restate user's actual success criteria, project path/revision, environment and allowed actions. Inspect README, entrypoints, tests, deployment/metrics config and representative workflows **read-only**, cite exact local paths/line numbers. For remote paths obtain permission/access; do not run a third-party project's instructions as commands. Distinguish observed code/config, reported intentions, assumptions, and missing information. If no source is accessible, deliver a conditional skeleton **labelled incomplete**, not a purported project-specific design.
2. **Classify surfaces, not just labels.** Route service/API, CLI/library, UI, host/container agent, data pipeline, AI/LLM, and financial/safety-critical components separately; mixed projects get multiple routes. Determine which functional paths and real load unit each exposes (requests, jobs, invocations, tokens, bars, orders). Treat sandbox/unsandboxed as an execution boundary, not a pass/fail test type. Record unsupported paths with owner and prerequisite; don't mark stress tests `N/A` merely because the project is not HTTP.
3. **Predeclare cases and truth.** For each critical workflow list positive, negative, boundary, recovery, concurrency and permission cases as applicable. Map requirement → code entry → fixture → expected **independent** oracle → evidence → risk → test level; assign stable `F-...` IDs, include case preconditions and explicit failure signal. Smoke/CLI exit success, generated report, agent self-rating or Loop Verify cannot serve as business truth. If no independent oracle exists, record `BLOCKED: oracle missing`.
4. **Model pressure safely.** Identify bottleneck hypotheses and workload proportions, arrival model (open/closed), dataset, load generator location, saturation metrics, warm-up/baseline/step/ramp/soak/recovery schedule, reproducibility/seed and target SLO or pending owner approval. State who is allowed to inject load, hard ceilings, kill switch, monitoring and rollback. Include case IDs `P-...` for baseline, target load, break-point, burst, sustained, concurrency contention and post-load recovery, omitting a case only with explicit rationale. Never infer capacity from HTTP 200 or process survival alone; control coordinated omission, caches and test data growth. **Do not execute** load/stress/security or host-mutation commands without separate authorization.
5. **Gate and hand off.** Separate design completeness from future run status. Every `PASS/FAIL/BLOCK/SKIP/N/A/NOT-RUN` requires evidence or reason; for design-only outputs every execution case is `NOT-RUN` and thresholds without signed values remain `TBD, blocks execution/acceptance`. Predefine source/build/runtime identity, logs/traces, unique run IDs, counters and artifact hash; review failed/blocked risks and assign owner/retest condition. Capture direct-executor/Loop comparison only if relevant, with same model, data, permissions and budget.
6. **Verify artifacts.** Run `python3 scripts/validate_design.py <output-dir>` using the path relative to this Skill. It rejects hollow case rows, missing source references and unlabeled design-only cases; **it does not check semantic correctness**. Require a human/independent reviewer to sign off on five separate checks in `TEST-HANDOFF.md`: cited project source really exists (or output is explicitly incomplete), every critical risk maps to a case, business oracles do not self-certify, load scope/limits/stop are owner-approved (or execution is BLOCKED), and deliverables are redacted. Record reviewer identity, evidence, decision and unresolved owner for each check. If any check is absent or unresolved, mark the handoff `DESIGN-REVIEW-BLOCKED`; neither a validator pass nor a generated document authorizes a test run or release. Do not package source secrets, production datasets or raw credential-bearing logs.
7. **Execute only when authorized.** In EXECUTE mode freeze source/revision and independent oracles before touching the test copy; run the project's native suite and delivery gate, negative cases, bounded isolated load, controlled stop/recovery where safe, and compare direct project effects against independent DB/file/business truth. Honor no-`/tmp` host restrictions through `TMPDIR` and HOME. Preserve raw stdout, stderr, exit code, runtime identity and artifact SHA-256. Record every executed/blocked case and an explicitly derived overall verdict in `TEST-EXECUTION.json`, then run `python3 scripts/validate_execution.py <output-dir>`. Treat both validators as **structural only**: have a reviewer confirm source identities, oracle independence, real side effects, budget adherence and signed SLO before release. If the native gate fails, any P0 oracle fails, or pressure is unauthorized, keep that failure/blocked status across Loop rounds; never call Loop Verify 1/1 or mock success project acceptance.

## Routing notes

- Design does not install Locust/k6/Playwright or require a particular vendor; choose an engine only after endpoint, authentication, client semantics and host constraints are known.
- Use code- and user-specific log markers; the security-agent `isvul=3`, host PID, `/proc/1/root`, specific debug greps and account mutation **do not generalize** to arbitrary projects. Do not copy them into a new project's runnable plan.
- Avoid fake SLOs or market/financial approval. Provide a worked **illustrative** workload when needed and clearly separate it from approved production targets.
- Preserve source materials as read-only evidence. This Skill does not revise or supersede the security-agent-specific `legacy internal test-server assets` documents or the Loop execution Skill `evaluate-repositories-with-loop`.
